# Deployment

This doc covers running the gateway + embedder stack in containers.
Navidrome is **not** part of the stack — point the gateway at an
existing Navidrome instance (anywhere reachable on the network).

The dev path (cargo + Vite + uv) lives in
[`GETTING-STARTED.md`](./GETTING-STARTED.md); use this doc when you're
deploying for real.

## What ships

Two containers:

| Container | Image tag (local) | Process | Ports | Volumes |
|---|---|---|---|---|
| Gateway | `crates-music/gateway:dev` | Rust binary + React SPA | `8443` (host) | `gw-data` → `/data` |
| Embedder | `crates-music/embedder:dev` | Python FastAPI (stub backend in Phase A) | `9000` (internal-only) | `gw-data` → `/data` (shared with gateway, see below) |

The gateway image bakes in the built SPA at `/etc/gateway/web/dist`
and serves it as a same-origin static site, so there's no separate
web container.

**Shared volume.** Both containers mount the same `gw-data` named
volume at `/data`. The gateway is the primary writer (OAuth state,
embeddings, caches, certs); the embedder writes only the UMAP
projection rows back into `gateway-state.recommend.sqlite` when the
gateway's auto-projection task asks it to. Both containers therefore
run as the same numeric uid (`10001`) so file ownership matches across
the boundary — pin Dockerfile changes to that uid, or the cross-write
breaks silently.

## First-boot sequence

```bash
# 1. Make sure Navidrome is reachable on the LAN.
curl -s http://nav.lan:4533/rest/ping?u=…&p=…&v=1.16.1&c=test&f=json

# 2. Copy the env template and fill in the three required values.
cp docker/.env.example .env
$EDITOR .env   # NAVIDROME_URL, NAVIDROME_USERNAME, NAVIDROME_PASSWORD

# 3. Build and bring up the stack.
docker compose up --build

# 4. The gateway logs a one-time setup token URL on first boot:
#       "gateway is unconfigured — visit https://0.0.0.0:8443/oauth/setup with token: …"
#    Open the URL in a browser (accept the self-signed cert warning),
#    set a master password, then sign in to the web app at the same
#    origin.
```

On second and later boots the gateway reuses the bearer token, TLS
cert, and OAuth state from the `gw-data` volume — nothing changes
unless you delete the volume.

## Environment reference

Everything is read from env vars at container start and templated into
`/data/config/gateway.toml`. Source of truth: `docker/gateway/gen_config.py`.

### Required

| Variable | Description |
|---|---|
| `NAVIDROME_URL` | e.g. `http://nav.lan:4533`. No trailing slash needed. |
| `NAVIDROME_USERNAME` | Navidrome admin account the gateway authenticates with. |
| `NAVIDROME_PASSWORD` | Plain-text Navidrome password. |

### Optional

| Variable | Default | Description |
|---|---|---|
| `GATEWAY_PORT` | `8443` | Host port to bind. Container always listens on 8443 internally. |
| `GATEWAY_HOSTNAME` | `gateway.local` | Hostname the auto-generated self-signed cert is issued for. |
| `GATEWAY_BEARER_TOKEN` | autogenerated | Legacy bearer used by the CLI. Persisted to `/data/state/bearer.token` on first boot if unset. |
| `OAUTH_WEB_REDIRECT_URIS` | `https://gateway.local:8443/oauth/callback` | Comma-separated list. Strict equality, no wildcards. |
| `EMBEDDER_URL` | `http://embedder:9000` (set by compose) | Sidecar base URL. Leave unset to run in degraded mode (no recommendations). |
| `EMBEDDER_TIMEOUT_SECONDS` | `30` | Per-request timeout. CPU-only CLAP can hit 10+ s. |
| `GATEWAY_TLS_CERT` | `/data/certs/gateway.local.pem` | Override to mount your own cert. |
| `GATEWAY_TLS_KEY` | `/data/certs/gateway.local-key.pem` | — |
| `GATEWAY_STATE_DB` | `/data/state/gateway-state.sqlite` | Override only if you split state across filesystems. |
| `GATEWAY_CACHE_DB` | `/data/state/gateway-cache.sqlite` | — |
| `GATEWAY_BROWSE_TTL_SECONDS` | `86400` | L2 metadata cache TTL. |
| `WEB_STATIC_DIR` | `/etc/gateway/web/dist` (set in the image) | Where the gateway serves the SPA from. Empty string disables static serving. |
| `RUST_LOG` | `info,music_gateway=info,sqlx=warn` | Tracing filter. |
| `EMBEDDER_BACKEND` | `stub` | `stub` (deterministic hash vectors) or `clap` (real model — Phase B). |

The web client (Phase B follow-up) and operator-mounted certs can ride
on the same env surface — see the `[server]`/`[oauth]` blocks in
[`CONFIGURATION.md`](./CONFIGURATION.md) for the underlying TOML schema.

## Resource limits & log rotation

The compose files cap each container's memory and rotate its JSON log
file by default. The intent is "an OOM in one container can't take the
host down, and `docker logs` can't fill the disk." Defaults:

| Service | Default `mem_limit` | Notes |
|---|---|---|
| `gateway` | `1g` | Mostly I/O bound. Bump if you raise the audio cache budget into the multi-GB range. |
| `embedder` (stub) | `512m` | Tiny — numpy + a couple of buffers. |
| `embedder` (CLAP CPU, `.clap.yml`) | `4g` | ~2 GB of float32 weights + librosa/torch working memory. |
| `embedder` (CLAP ROCm, `.clap-rocm.yml`) | `6g` | Model lives on the GPU; CPU mirror + MIOpen JIT pipeline costs ~5 GB sustained. |
| `navidrome-stub` (smoke profile) | `128m` | One-file Python server. |

All capped via env in `.env`:

```
GATEWAY_MEM_LIMIT=2g
EMBEDDER_MEM_LIMIT=8g     # honoured by base + both CLAP overrides
```

JSON log rotation is global:

```
LOG_MAX_SIZE=10m          # per file
LOG_MAX_FILE=3            # rotated files retained
```

Logs are still streamed live via `docker compose logs -f`; rotation
only governs the on-disk JSON tail.

If a container hits its memory cap, Docker OOM-kills it and `restart:
unless-stopped` brings it back. Check with `docker inspect <id> --format
'{{.State.OOMKilled}}'` after a crash — if `true`, raise the cap.

## Volumes

One named volume, `gw-data`, mounted at `/data` in the gateway container.
Layout under `/data`:

```
/data/
├── config/            # generated gateway.toml (inspect when debugging)
├── certs/             # gateway.local.pem + key (self-signed on first boot)
├── state/
│   ├── gateway-state.sqlite              # OAuth: users, clients, tokens
│   ├── gateway-state.recommend.sqlite    # embeddings, ingest queue, events
│   ├── gateway-state.traces.sqlite       # diagnostics ring
│   ├── gateway-state.ann                 # HNSW mmap
│   ├── gateway-state.ann.keys            # ANN ↔ track-id sidecar
│   ├── gateway-cache.sqlite              # L2 metadata cache (disposable)
│   └── bearer.token                      # autogenerated, mode 0600
└── audio/             # L4 transcoded-stream cache (when implemented)
```

The embedder is stateless in Phase A and doesn't mount any volumes.

### uid alignment

Both containers run as the same numeric uid (`10001`) and gid (`10001`)
so the embedder can write into `gateway-state.recommend.sqlite` after
the gateway opened it. If you're carrying a `gw-data` volume from a
build that predates this pin, the files inside are owned by whatever
uid `useradd --system` happened to allocate at image-build time
(typically `999`). Rebuild against the new images and either:

- start fresh (`docker compose down -v`, lose the volume — fine on a
  first-deploy machine), or
- one-shot chown the volume contents to `10001:10001`:

```bash
docker run --rm -v cratesmusic_gw-data:/data alpine \
    chown -R 10001:10001 /data
```

### What to back up

**Critical, can't be re-derived from anywhere:**

- `state/gateway-state.sqlite` — OAuth refresh tokens, users, clients. Lose
  this and every paired device has to re-pair.
- `state/gateway-state.recommend.sqlite` — embeddings + event log. Lose this
  and you re-compute every track embedding from scratch (slow with CLAP).
- `state/bearer.token` — legacy CLI auth. Cheap to regenerate but every CLI
  has to be reconfigured.
- `certs/` — only if you've replaced the self-signed cert with one you
  paid for.

**Don't bother backing up** (rebuild on demand):

- `gateway-cache.sqlite` — L2 metadata cache. Re-fetches from Navidrome.
- `gateway-state.ann` / `.ann.keys` — derived from `recommend.sqlite`,
  rebuilt at boot.
- `gateway-state.traces.sqlite` — diagnostics ring, write-only-recent.
- `audio/` — transcoded-stream cache. Regrows from Navidrome.

## Health endpoints

Two endpoints, intentionally distinct:

| Endpoint | Purpose | Status |
|---|---|---|
| `GET /healthz` | **Liveness.** Process is up and the axum runtime is serving. Always 200. Use this when you want "should I restart the container?" semantics. | 200 always |
| `GET /readyz` | **Readiness.** Probes upstream Navidrome (Subsonic `ping`, 2 s timeout) and the configured embedder. Use this when you want "can this container actually serve traffic right now?". | 200 ready, 503 degraded |

The container `HEALTHCHECK` is pointed at `/readyz`, so a Navidrome
outage (or a configured-but-unreachable embedder) flips the gateway
container to `unhealthy` within one healthcheck interval (~30 s). This
is what makes `depends_on: service_healthy` meaningful for any future
service we layer in front (e.g. a reverse proxy).

`/readyz` response shape (degraded example):

```json
{
  "status": "degraded",
  "service": "music-gateway",
  "checks": {
    "navidrome": { "status": "error", "error": "..." },
    "embedder":  { "status": "ok", "dim": 512 }
  }
}
```

Embedder check semantics:

- No `[embedder]` block → `"status": "disabled"` (not a failure).
- Configured & last probe saw the model loaded → `"status": "ok"`.
- Configured & last probe was unreachable / loading → `"status": "error"` and overall 503.

## TLS

The entrypoint mints a self-signed cert for `$GATEWAY_HOSTNAME` (default
`gateway.local`) on first boot if `/data/certs/` is empty. Pros: no
external dependencies, the gateway starts on first launch with no
manual steps. Cons: every client has to accept a security warning the
first time it connects.

**Production paths:**

1. **Mount your own cert.** Drop PEM-encoded `gateway.local.pem` and
   `gateway.local-key.pem` into the `certs/` subdirectory of the
   `gw-data` volume before first boot. The entrypoint detects existing
   files and skips the self-sign step.
2. **Reverse proxy with public TLS.** Put Caddy or Traefik in front
   of the gateway. The internal gateway can still use a self-signed
   cert (the proxy terminates real TLS). You'll want to point
   `OAUTH_WEB_REDIRECT_URIS` at the public URL.

mDNS / `/etc/hosts` on each client device is the path for option 1
(`gateway.local` → the gateway IP). Mobile devices on Android can
install the cert as a user CA from Settings → Security.

## Updates

```bash
git pull
docker compose build
docker compose up -d
```

The named volume persists across image rebuilds, so OAuth state,
bearer tokens, certs, and embeddings all carry over. The container
restarts in a few seconds — the rebuild is the long part (Rust
release build of the workspace).

## Debugging

Show recent logs:

```bash
docker compose logs --tail=100 gateway
docker compose logs --tail=100 embedder
```

Inspect the generated config (handy when "the gateway is reading the
wrong Navidrome URL" suspicions arise):

```bash
docker compose exec gateway cat /data/config/gateway.toml
```

Read the autogenerated bearer token (CLI uses this):

```bash
docker compose exec gateway cat /data/state/bearer.token
```

Probe the embedder from inside the gateway container:

```bash
docker compose exec gateway curl -s http://embedder:9000/healthz
```

Drop into a shell:

```bash
docker compose exec gateway bash    # gateway runs as the `gateway` user
docker compose exec embedder bash   # embedder runs as the `embedder` user
```

## Running with CLAP (real embeddings)

The default `embedder` service runs the **stub backend** — deterministic
SHA-256-seeded hash vectors. Good enough for OAuth / sync / proxy smoke
tests, but recommendations from stub embeddings have no acoustic
meaning. For useful recommendations, swap to the CLAP variant.

Phase B step 1 ships a **CPU-only** CLAP image. Same Python sidecar,
real LAION CLAP inference, no GPU passthrough required. Slower than
the future ROCm variant (~30–90 s checkpoint load on boot, ~1 s per
embed on a modern x86-64 core), but hermetic and reproducible.

```bash
# 1. Drop a CLAP checkpoint somewhere on the host. The codebase has
#    been smoke-tested against LAION's music-audioset weights
#    (`music_audioset_epoch_15_esc_90.14.pt`, ~2.2 GB). Other LAION
#    CLAP checkpoints work; non-LAION ones do not.
ls ./models/music_audioset_epoch_15_esc_90.14.pt

# 2. Point CLAP_CHECKPOINT_PATH at it in .env.
echo 'CLAP_CHECKPOINT_PATH=./models/music_audioset_epoch_15_esc_90.14.pt' >> .env

# 3. Bring the stack up with the CLAP override file. The base
#    docker-compose.yml stays the source of truth; the override only
#    replaces the `embedder` service's image + env + volume.
docker compose -f docker-compose.yml -f docker-compose.clap.yml up --build
```

What changes vs. the stub deploy:

| | Stub (default) | CLAP CPU |
|---|---|---|
| Image | `crates-music/embedder:dev` (~350 MB) | `crates-music/embedder-clap:dev` (~3 GB) |
| First-boot time to healthy | ~5 s | 30–120 s (checkpoint load) |
| `/healthz` `device` field | `cpu` | `cpu` (CUDA-disabled torch) |
| `model_version` | `stub-v1` | derived from checkpoint filename |
| Per-embed latency | ~0.5 ms | ~700–1500 ms |

The checkpoint is bind-mounted **read-only** at `/models/clap.pt` inside
the container. We deliberately don't bake it into the image —
checkpoints are large (2+ GB) and LAION's weights ship under a
research-use license that's awkward to redistribute in a Docker tag.

The embedder healthcheck `start_period` is `120s` in the CLAP image
(vs `10s` for the stub) — that's what makes `depends_on:
service_healthy` on the gateway work without races during a cold
boot.

## Running with CLAP on AMD ROCm GPU

Phase B step 2: same CLAP backend, PyTorch built against ROCm 6.4
instead of CPU wheels. ~6× faster than the CPU variant on an RDNA4 GPU
(per-embed latency drops from ~1 s to ~150 ms). Requires an AMD GPU
that ROCm 6.4 supports — gfx1100 (RDNA3) and gfx1201 (RDNA4) are
covered by the bundled wheel runtime.

```bash
# 1. Same checkpoint as the CPU variant.
echo 'CLAP_CHECKPOINT_PATH=./models/music_audioset_epoch_15_esc_90.14.pt' >> .env

# 2. Tell compose your host's render/video group IDs. Check with:
#       getent group render video
#    Defaults in the compose file are Arch/Cachy (render=988, video=984).
#    Debian/Ubuntu typically use render=109, video=44.
echo 'RENDER_GID=988' >> .env
echo 'VIDEO_GID=984' >> .env

# 3. Bring the stack up with the ROCm override.
docker compose -f docker-compose.yml -f docker-compose.clap-rocm.yml up --build
```

Differences from the CPU variant:

| | CLAP CPU | CLAP ROCm |
|---|---|---|
| Base wheel index | `whl/cpu` | `whl/rocm6.4` |
| Image size | ~4 GB | **~23 GB** (rocm6.4 torch wheel unpacks the entire ROCm runtime) |
| Device passthrough | none | `/dev/kfd` + `/dev/dri` |
| Group membership | none | `render`, `video` (host GIDs) |
| `/healthz` `device` field | `cpu` | `cuda` (torch reports AMD GPUs as "cuda") |
| First audio embed (cold MIOpen cache) | n/a | ~2.5 s |
| Subsequent audio embed (1 s clip) | ~113 ms | ~36 ms |
| Text embed | ~170 ms | ~50 ms |
| Healthcheck `start_period` | 120 s | 60 s |

**MIOpen cold-cache penalty.** The first audio embed after any
container restart compiles GPU conv kernels into
`/var/cache/miopen/` inside the container. That's ~2.5 s of one-off
latency on the first inference of each container lifetime; everything
afterwards is fast. The cache lives in the container's writable
layer and is discarded by `docker compose down` — restarts always
eat the cold-cache cost once. If that matters for ythis deployment,
mount a named volume at `/var/cache/miopen` to persist it.

**Verifying GPU is actually being used.** After the container is
healthy, hit `/healthz` on the embedder directly and look for
`"device": "cuda"`. If it reports `"cpu"`, either the device
passthrough didn't land, the user wasn't in the right groups, or
the wheel's ROCm runtime doesn't have kernels for your card — in
that order of likelihood. Logs from `docker compose logs embedder`
will say `CLAP loaded on device=cpu` in the silent-fallback case.

**`HSA_OVERRIDE_GFX_VERSION`.** Not set by default. The rocm6.4
wheels cover gfx1100 and gfx1201 natively, so an unconditional
override would *mis*-route kernels on the cards that need them
least. Set it only as a workaround when `rocm-smi` sees your card
but torch reports `cuda.is_available()` as false inside the
container — see the commented entry in `docker-compose.clap-rocm.yml`.

A **GPU variant for NVIDIA** is not in scope — the codebase has
been developed and tested on AMD; CUDA-flavoured CLAP would mean a
third Dockerfile and a different wheel index, and there's no
hardware to validate it against.

## Known limitations (Phase A + B)

- **No multi-arch builds.** x86-64 only; ARM hosts (Pi 5, Apple
  Silicon) will fail to pull any of the three embedder images. The
  CLAP variants are especially x86-64-pinned because the PyTorch
  CPU+ROCm wheels are.
- **No CI pipeline.** Images are built locally. GitHub Actions matrix
  build + GHCR push is Phase D.
- **No automatic cert rotation.** The self-signed cert expires after
  825 days; replace by stopping the stack, deleting `certs/*.pem` from
  the volume, and starting again.
